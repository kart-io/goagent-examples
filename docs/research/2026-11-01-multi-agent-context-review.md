## 正式发现

### R-01 · P2 · 恢复路径没有闭合固定锁顺序

位置：第 10.3 节 L384；第 10.4 节 L415、L421。

正常提交规定“当前任务/调用资格提交保护 → 文件资源锁”。恢复要求在文件锁中先处理旧 PreparedCommit，必要时核验旧任务资格并重试，但没有规定如何在不倒置锁顺序的情况下取得旧任务的提交保护。

可导致死锁的交错：

1. A 已保存 PreparedCommit 后退出，留下待核对记录。
2. B 持有 B 的任务保护和文件锁，发现 A 的未结清记录。
3. A 的重试持有 A 的任务保护，等待文件锁。
4. B 为核验和继续 A 的旧提交而等待 A 的任务保护，形成循环等待。

即使没有 B，恢复若先取文件锁、再取任务保护，也会与正常提交形成相反的锁顺序。设计不一定必须采用上述恢复实现，但目前没有排除该路径。

**最小修订：**正常提交、恢复、查询补记共用同一锁协议。仅持文件锁时可读取待核对记录；若必须取得记录所属任务的保护，则先释放文件锁以及无关的新任务保护，再按“原任务保护 → 文件锁”获取，并重新核验该准备记录、版本及资格。禁止持新任务保护再获取另一任务保护。W 声明多进程范围时，任务保护也必须是跨进程共享保护，不能只有文件锁共享。

**建议验收：**用屏障固定上述 A/B 交错；验证正常提交与恢复都能退出，不重复应用补丁，旧准备记录未结清时新提交不越过。

### R-02 · P2 · 其他资格版本更新未明确参与最终提交保护

位置：第 7.3 节 L174，第 8.4 节 L251，第 10.2 节 L375，第 10.3 节 L384。

最终文件提交要复验任务、依赖、规则版本等，但只明确要求任务修订或取消的更新遵守提交保护。GrantsVersion、RulesVersion、InvocationEpoch、候选和已采纳依赖的更新是否参与同一保护尚未明确。

失败交错：提交者在保护中完成最后复验 → 规则或授权更新者不经过该保护而改变版本 → 提交者 rename 成功。文件可能按已经失效的规则或资格生效，与“授权撤回使旧调用失去采纳资格”“旧规则提案不得提交”不一致。

**最小修订：**枚举全部影响提交资格的权威状态，其更新与最终提交必须在共同保护/事务下排序：任务修订、InvocationEpoch、取消、候选、已采纳依赖、GrantsVersion、RulesVersion。全局规则/授权更新也需声明兼容的锁顺序或事务生效协议，不能只要求提交者重复读取。

**建议验收：**在最后复验与文件替换之间并发撤回授权/更新规则/替换调用；结果只能线性化为“旧提交先完成”或“更新先完成、旧提交拒绝”，不能出现更新已生效后旧资格仍落盘。

## 实施前需要明确的治理接线

下述不是已经证明无法落地的设计缺陷：文档允许宿主调度器，公开钩子及适配层可承接治理；token 准入又是条件启用。它们仍需在 P1 实施计划中作出明确选择，避免按错误方式接线。

### I-01 · 预算预留应有唯一所有者，限流顺序不能只靠客户端包装猜测

位置：第 8.6 节 L269–L281。

固定实现的 [builder/model_call.go](https://github.com/kart-io/goagent/blob/da848ae/builder/model_call.go#L68) 在内部派生 AttemptKey，并在调用模型客户端之前执行 Reserve；[core/budget/attribution.go](https://github.com/kart-io/goagent/blob/da848ae/core/budget/attribution.go#L88) 拒绝相同键重复预留。

若仅在客户端包装中实施文档“先请求槽、再 Reserve”，实际顺序已是 Builder Reserve → 包装层：再次 Reserve 同键会拒绝，换键会双计数；只限流又不能兑现原文指定顺序。

**建议明确：**Builder 是当前调用链预算预留与证据记录的唯一所有者，宿主不二次 Reserve。若保留“先槽后预留”，实施计划需说明首请求和每次重试如何用公开宿主钩子在内部预留前取得槽，以及预算拒绝、取消、预处理失败和流结束时如何准确释放。另一种选择是明确接受“Builder 保守预留 → 共享传输槽 → 发请求”的顺序及排队取消不返还预留的语义；这属于需要主动修改的契约选择，不能混用。

API 审阅者提出候选 P2；主审将其列为接线澄清，因为文档并未限定只能使用客户端包装，也没有要求宿主重复预留，不能仅凭最简单接法错误就断言方案不可实现。

### I-02 · token 超估后的停派是额外的宿主规则，不由 RecordEvidence 自动完成

位置：第 8.6 节 L283。

[ReserveAttributed](https://github.com/kart-io/goagent/blob/da848ae/core/budget/attribution.go#L94) 按估计预留额度；[RecordEvidence](https://github.com/kart-io/goagent/blob/da848ae/core/budget/attribution.go#L109) 合并实际证据，不修改原 Estimate。KnownTokenDelta 是统计信息，并非自动的停派门闩。

例如额度 100、A 估计 10 但实际 100：记录 A 的用量后，Controller 仍可按估计为 B 预留 10。若要求实际超估后停止新的发送，而宿主异步处理停派通知，B 可能在停派生效前发送。

**建议选择其一：**P1 仅启用请求硬上限和 token 观测，明确不开启基于实际超估的额外 token 停派承诺；或者实现共享的宿主准入状态，明确实际用量更新、超估规则和新请求发送资格检查的共同原子边界。已经在途的请求不倒退成“没有发送”。

API 审阅者提出候选 P2；主审将其列为条件功能的实施前澄清，因为文档已明确 token 估计不等于账单硬上限，并未声称 Controller 自动按实际值退还/收紧额度。若决定启用该停派功能，则必须在实现前关闭此接线缺口。

## 其他非阻塞注意事项

1. **Workspace 级幂等登记。**文档已经要求 `(WorkspaceID, ChangeID)` 唯一；实现需用原子登记/唯一约束绑定 ProposalDigest 和 ResourceKey，不能只在各自文件锁里检查。该不变量已声明，具体索引/登记实现留给实施计划，不另报设计缺陷。
2. **稳定文件锁身份。**锁不能只依附于会被 rename 替换的 inode；应使用稳定资源键和共享锁载体，并保持路径别名归一规则。文档已有相应身份要求。
3. **Fork 的 ProviderState。**[llm/client.go](https://github.com/kart-io/goagent/blob/da848ae/llm/client.go#L36) 和 [gemini_native.go](https://github.com/kart-io/goagent/blob/da848ae/llm/providers/gemini_native.go#L100) 要求某些不透明原生状态与原消息一致。F 验收应区分可见 ReasoningContent 与 ProviderState；不能泛化为删除 reasoning 字段后仍保证原生工具历史可回放。无法授权或合法重建时按现有设计拒绝 Fork/回退 Brief，因此不构成额外阻塞。

## 已确认设计成立的部分

- 默认按角色传充分的 Brief，并保留硬约束、否定条件、已确认决定和暂时假设的区别。
- 编排方式与 brief/fork_snapshot 正交，指定快照位置、独立子会话和 frozen 更新规则明确。
- ExecutionStatus、BusinessConclusion、AdoptionStatus 三轴及下游路由明确。
- 绑定输入、候选和已采纳上游报告；原子采纳包含迟到、取消、替代及重复报告检查。
- 证据校验不局限于引用存在或哈希正确，包含差旅域的主张支持性核对。
- 原始基线、ExpectedCurrentHash 和 NewHash 分开；未结清提交先核对；单文件与跨文件保证范围分开。
- P1/F/W/P2 分工及三平台真实验收位置一致，不需要将 P2 的持久历史产品功能提前塞进 P1。
