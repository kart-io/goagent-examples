# 客服编排测试页面设计

日期：2026-11-17

## 意图

为 `orchestration/customer-service` 补充浏览器页面，手动测试长期记忆（以及整条客服流程）。现在只能逐条敲 CLI 命令，每条命令都是新进程，看不到连续对话，也不方便同时扮演客户和客服两个角色。

## 目标

1. **用户页面**：以客户身份发消息、看客服回复，像聊天一样连续进行。
2. **客服页面**：客服角色由 Agent 接管（分流、退款、通用成员自动回复），人只在需要时介入：
   - 审核：退款进入审核时批准或驳回（现有 `answer`）；
   - 人工回复：工单转人工（handoff）后由人直接回复客户（新增能力）；
   - 运营：手动执行 `sweep`、查看当前客户的记忆。
3. 记忆面板：钉住记忆、按文本召回、按 ID 查看单条记录（含已被取代或失效的旧记录，用来判断钉住继承）。
4. 与 CLI 行为一致：页面调用的就是宿主现有方法，测出来的是同一套行为。

## 非目标

- 不做登录与鉴权：本地测试工具，只监听本机地址。
- 不做真实 IM 渠道、推送（WebSocket/SSE）：页面定时刷新即可。
- 不做记忆编辑；删除记忆（forget）也不做（CLI 没有，范围外）。
- 不改工单流程、分流规则与记忆接线本身。
- 不做时钟控制：serve 用真实时钟，审核超时、追问超时、提醒仍用 CLI 的 `-now` 演示。页面上的 sweep 主要用于处理记忆抽取任务和重投发件箱。

## 反目标

- 页面或接口能让客户看到或影响其他客户的工单与记忆。
- Agent 运行时的记忆命名空间改为取自页面参数：运行时仍只取工单行的 CustomerID；记忆面板只读，命名空间取自所选客户 ID（与 CLI `memory -customer` 相同）。
- 未开启 `-memory` 时现有 CLI 行为或测试发生变化。
- 页面、接口或日志输出 API key、数据库连接串。

## 约束

- 沿用 feat/cs-memory 分支与工作区模式（`make work CONTRIB=...`），不发版。
- 只用标准库 `net/http` 与 `go:embed`，页面为纯 HTML + 少量原生 JS，不引入前端构建链或新依赖。
- 一个常驻进程持有一个宿主（账本 SQLite、记忆连接）；同一 `-dir` 不应同时运行 CLI 写命令（与现有约定一致）。
- 测试运行：`TMPDIR=/tmp taskset -c 2,3,6-27`；需要容器的测试经 `scripts/with-stores.sh`。

## 方案

| 方案 | 内容 | 取舍 |
|---|---|---|
| **A（选定）** | 新增 `serve` 命令，常驻宿主 + JSON 接口 + 内嵌两个静态页面 | 无新技术栈，直接调用宿主方法；参照 knowledge-assistant 的 `internal/web` |
| B | 独立前端工程（React/Vite）+ Go 接口 | 界面好做，但多一套构建链与 node 依赖，对测试示例负担过重 |
| C | 页面后台逐条调用 CLI 进程 | 改动最少，但每次重开账本与记忆连接，慢，看不到实时回复 |

用户选择 A。

## 设计

### 1. `serve` 命令

`customer-service serve -dir D [-addr 127.0.0.1:8090] [-memory ...] [-live]`

- 打开宿主（与其他命令相同的 `HostConfig`，含 `-memory`、`-live`、`-approvers`），直到收到中断信号再关闭。
- `-addr` 默认只监听 127.0.0.1。
- 写操作串行：发消息、审核、人工回复、sweep 由一把互斥锁串行执行。
- 写操作异步：`Host.Message` 和 `Host.Answer` 会同步跑完整个模型运行，`-live` 时可能要几十秒。所以接口校验参数后立即返回 202，由后台协程持锁执行。页面在回复出现前显示"处理中"；执行出错时，错误记在内存里，按消息 ID 查询（重启丢失可以接受）。人工回复和 sweep 耗时短，同步执行。
- 读操作不加锁：账本 SQLite 只有一个连接（`SetMaxOpenConns(1)`，`busy_timeout=5000`），写事务很短，模型运行在事务外，所以读接口可以和后台运行并发。
- 通知器沿用 `printer`，JSON 行打到标准输出，作为运行日志。页面不依赖它，只读账本发件箱，所以服务重启后对话仍在。

### 2. 接口（JSON，仅供本页面使用）

客户侧：
- `POST /api/customers/{c}/messages` `{message_id, text}`：后台调用 `Host.Message(c, "agent-1", message_id, text)`，返回 202。消息 ID 由页面生成，重试时复用，宿主按消息 ID 去重。submitter 用演示客服账号 `agent-1`。
- `GET /api/customers/{c}/conversation`：返回该客户所有工单的对话，按时间合并。
  - 客户消息取自 `ticket_messages`。每条消息（包括开单那条）都会写入这里，所以 `tickets.input` 被新一轮覆盖时不会丢消息。
  - 客服回复只取 outbox 中 `channel=notify` 且 recipient 为该客户的记录。`channel=handoff` 记录的 payload 是内部交接摘要，不能出现在客户页；客户看到的是同一次转人工时写入的 `handoff_notice` 通知。
  - 每条带工单 ID、时间和投递状态，另附后台尚未完成的消息 ID 及其错误。
  - 排序：两张表没有共同的时间轴（各自独立的 `seq`），所以账本升到 `schemaVersion = 2`，给 `ticket_messages` 和 `outbox` 加 `created_at` 列（宿主时钟，RFC3339Nano）。按 `created_at` 排序；时间相同时客户消息在前，其次按各表 `seq`。旧的 v1 目录按现有规则报"账本结构不兼容，请换用新的演示目录"，不做迁移。

客服侧：
- `GET /api/tickets[?customer=c]` → 工单列表：ID、客户、状态、轮次、最后进展时间，以及派生标记 `needs_human`（定义见第 4 节）。
- `GET /api/tickets/{t}` → `Host.Show` 的内容，加上 Agent 处理过程（检查点里的 turns：哪个成员、输出什么），用于"看 Agent 怎么处理的"。
- `POST /api/tickets/{t}/answer` `{approver, approve, note}` → 后台调用 `Host.Answer`，返回 202；审核人从工单的 approvers 中选。
- `POST /api/tickets/{t}/reply` `{reply_id, staff, text}` → 人工回复（新增，见第 4 节），同步执行。
- `POST /api/sweep` → `Host.Sweep`，返回 `SweepReport`。
- `GET /api/customers/{c}/memories[?q=]`、`GET /api/customers/{c}/memories/{id}` → `Host.Memories`、`Host.MemoryRecord`；未开启 `-memory` 时返回明确的"未开启长期记忆"错误。

错误统一为 `{"error": {"code", "message"}}`，消息用中文，经 `livemodel.Redact` 处理。

### 3. 页面

`go:embed` 两个页面与一个共用的小脚本：

```
/customer  用户页面
┌─────────────────────────────────────────┐
│ 客户：[c-1001 ▼]                          │
│ ┌─────────────────────────────────────┐ │
│ │ 我：订单 A1001 申请退款 30 元          │ │
│ │ 客服：已为您提交退款，等待审核……       │ │
│ │ 我：请记住：只用邮件联系我             │ │
│ │ 客服：好的，已记住。                   │ │
│ └─────────────────────────────────────┘ │
│ [输入框                         ] [发送] │
└─────────────────────────────────────────┘

/desk  客服台（Agent 接管）
┌──────────────┬────────────────────────────────┬──────────────────┐
│ 工单列表      │ 工单 tk-… 状态 waiting_review   │ 记忆（客户 c-1001）│
│ ● tk-… 待审核 │ 客户消息 / Agent 处理过程        │ 钉住：…           │
│ ○ tk-… 已送达 │  分流→退款→提议 refund 3000 分   │ 召回 [文本][查]   │
│ ○ tk-… 待人工 │ [批准][驳回] 审核人[fin-1 ▼]    │ 记录 ID [  ][查]  │
│ [执行 sweep]  │ 人工回复（仅待人工）[    ][发送]  │ superseded_by …  │
└──────────────┴────────────────────────────────┴──────────────────┘
```

- 两个页面每 2 秒左右刷新一次当前视图。
- 客户下拉默认含演示订单所属的 `c-1001`、`c-2002`，也可输入任意客户 ID（没有订单的客户只能测通用咨询与记忆）。
- 客服台的记忆面板跟随当前选中工单的客户。

### 4. 人工回复（新增能力）

- **待人工不能看 `tickets.status`**：`deliver()` 在发件箱全部发出后，会把 `done/handoff/failed` 的工单改成 `delivered`，所以 handoff 状态几乎马上就消失了。
- **"转过人工"的判定**：工单在发件箱中有 `channel=handoff` 的记录。分流转人工（handoff）和运行失败（failed）都会写这条记录，两者都算。
- **允许人工回复的条件**：工单转过人工即可，可以回复多次。没有转过人工的工单返回冲突错误。
- **`needs_human` 标记**：工单转过人工，且最后一条 handoff 记录之后还没有人工回复。人工回复后标记消失，因此不需要新增工单状态，也不改 `tickets.status`。
- **写入方式**：写入账本发件箱一条发给该客户的 `channel=notify` 通知，复用现有投递路径，所以客户页能看到、重启不丢。
  - 幂等键为 `<ticket>/manual/<reply_id>`。`reply_id` 由页面生成，重试时复用，重放不会重复发送。
  - 通知 kind 用现有的 `support.KindCustomerReply`，标题为"人工客服"。按幂等键前缀 `/manual/` 区分人工回复。
- **不进记忆**：人工回复不进入 Agent 的会话日志，长期记忆不会从中抽取，记忆只学 Agent 参与的对话。README 写明。
- **客户再发消息**：按现有规则新建工单，交给 Agent。

### 5. 验证

- 接口测试（`net/http/httptest`，离线模型，表驱动）：
  - 客户发消息后，对话接口能看到客户消息与回复，且按顺序交错（多轮工单的第 1 轮消息也在）；
  - 客户 A 的对话与记忆接口看不到客户 B 的数据；
  - 转人工工单的对话只出现 `handoff_notice`，不出现交接摘要内容；
  - 审核接口批准后工单推进（测试轮询直到状态变化，不 sleep 固定时长）；
  - 人工回复：工单已变为 `delivered` 时仍可回复；没有转过人工的工单返回冲突；同一 `reply_id` 重复提交只投递一次；回复后 `needs_human` 变为假；
  - 后台执行出错时，对话接口能看到该消息的错误；
  - 未开启 `-memory` 时，记忆接口返回明确错误，其他接口正常，且不需要容器；
  - 开启记忆（经 with-stores.sh）：发"请记住：……"后，记忆接口的 pinned 立即有 1 条（`memory_save` 在 Agent 运行时直接写入，不需要 sweep）；sweep 接口返回 MemoryJobs；
  - 现有 CLI 测试在账本 v2 下全部通过。
- 页面：用浏览器手动走一遍（离线，再用 `-live`）：用户页发退款与"请记住"，客服台审核、执行 sweep、查看记忆与旧记录。

## 已定的实现细节（设计者的决定，可推翻）

- 默认监听 `127.0.0.1:8090`，页面每 2 秒刷新一次，submitter 固定为 `agent-1`。
- 发消息和审核异步执行（202 + 轮询），人工回复和 sweep 同步执行；写操作共用一把锁，读操作不加锁。
- 账本升到 v2，加 `created_at` 用于排序，旧目录不迁移（沿用现有"不兼容就换目录"的做法）。
- "待人工"由发件箱 handoff 记录派生，不改 `tickets.status`，不新增状态；failed 工单同样算待人工。
- 人工回复的幂等键由页面提供的 `reply_id` 构成，kind 为 `KindCustomerReply`，标题为"人工客服"。
- 通知器沿用 `printer`。
- 不做时钟控制。

## 风险

- 宿主原本按"每条命令一个进程"设计，常驻后长时间持有锁或连接的行为需要确认（`LockTimeout`、记忆 Worker 锁只在 sweep 时取）。
- 页面轮询与后台运行并发：读操作靠 SQLite 单连接与短事务保证一致；单个连接上读请求会排队，等待时间通常是毫秒级。
- 后台协程在关闭服务时可能还在跑模型：关闭时先停止接收请求，再等后台任务结束（或超时），然后关闭宿主。
- 账本 v2 会让已有的演示目录无法再用（需要换目录），README 写明。
